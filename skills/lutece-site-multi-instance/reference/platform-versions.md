# Platform versions

The plugin fixes a site needs to run on several replicas (shared session, shared cache, concurrent replicas) are carried by
the BOM and the starters of `lutece-platform` **8.0.0-beta-04** or later: `fr.paris.lutece.starters:lutece-bom` imported in
`dependencyManagement`, a starter (`forms-starter`, `appointment-starter`, `editorial-starter`, `lutece-starter`) or the
organisation's pack built on them. The layers and the rules of the site pom are in `lutece-update-site`
(`reference/layers.md`).

Check, on the site and on its assembled war:

1. The `lutece-bom` import and the starter are at 8.0.0-beta-04 or later.
2. No artefact the BOM manages carries a version of its own in the site pom (`site_check.py` SI04): an older version pinned
   there brings back the defect the BOM fixes.
3. The `cluster` profile adds `library-cache-hazelcast` (managed by the BOM): without it every Lutece cache holds 10,000
   entries under Hazelcast, whatever its Lutece size.
4. An artefact outside the BOM (a plugin of another team, a site-specific module) is not covered: report it, and review its
   code with `lutece-scalability-v8` before running it on several replicas. Do not patch it from the site.

While the site cannot reach that level: one replica, or session affinity at the load balancer, no form with a quota, no
numbering entry and no attachment field.

## Plugin code the BOM cannot fix

Plugin code storing per-item session attributes (one attribute per token, per uploaded file, created and removed at run time)
does not survive node switches with OpenLiberty `sessionCache`: an instance that already holds the session in memory misses
the attributes created on another instance (reproduced: a form step alternating 1-2-1-2 loses its state, an upload on one
instance is missing on the next step on the other). Keep one attribute per concern (a map) whose value changes; the remaining
limit is two concurrent requests of one session on two instances (last write wins).

Locks (`synchronized`) on DAO inserts protect nothing: keys are generated by the database. They only serialize the hot paths
of one replica; removing them is safe.
